# 用户服务设计

## 1. 模型总览

用户体系分为四层：身份层（users/account）→ 档案层（students/teacher_list）→ 角色层（role/user_role）→ 数据范围层（sys_organization）。

所有用户、账号、角色和组织权限均位于当前学校业务库。主库仅保存租户信息，不保存自然人、账号或角色。若同一企业微信用户属于多个学校，需要在各学校租户库内分别完成绑定，各学校之间不共享 users/account 数据。

```

│    users         │  ← 自然人基础信息（与企业微信绑定在这层）
│  - id            │
│  - name          │
│  - wechat_userid │
│  - phone         │
│  - avatar        │
│  - ...           │
└────────┬─────────┘
         │ 1:N（当前学校库内一个人可有多个系统账号）
         │
```

## 2. 数据模型

### users（自然人）

```
users
  - id, name, name_spell
  - wechat_userid（企业微信唯一 ID，与 user_wechat 表关联）
  - phone, email, sex, birthday
  - avatar, status
  - created_at, updated_at, deleted_at
```

### user_wechat（企业微信档案）

```
user_wechat
  - id, user_id（一对一关联 users）
  - wechat_userid（企业微信用户 ID，唯一）
  - wechat_name（企业微信姓名）
  - wechat_avatar（企业微信头像 URL）
  - department（JSON，企业微信部门 ID 列表，用于匹配学院）
  - position（职务）
  - mobile（企业微信绑定手机）
  - email（企业微信绑定邮箱）
  - gender
  - raw_data（JSON，完整 OAuth 返回数据，用于排查）
  - last_synced_at（最后一次同步时间）
  - created_at, updated_at, deleted_at
```

**同步策略：** 每次通过企业微信 OAuth 登录时，拉取最新用户信息写入 user_wechat。department 字段用于自动匹配 school 下的学院/部门。

### account（系统账号，每库一个学校）

```
account
  - id, uuid
  - user_id（关联 users）
  - password（`password_hash($pwd, PASSWORD_BCRYPT)` 自动加盐，管理员密码登录用，可为空）
  - two_factor_secret（TOTP 密钥，AES-256-GCM 加密存储，可为空）
  - two_factor_enabled: false / true（默认 false）
  - status: enabled / disabled
  - created_at, updated_at, deleted_at
```

### role（角色）

```
role
  - id
  - code: super_admin / school_admin / college_admin / profession_admin / teacher / student / enterprise
  - name（角色名称）
  - role_type（角色类型，同 code）
  - sort, status
  - created_at, updated_at, deleted_at
```

### user_role（账号-角色关联）

```
user_role
  - id
  - account_id（关联 account.id）
  - role_id（关联 role.id）
  - is_primary: false / true
  - created_at, updated_at, deleted_at
```

### sys_organization（角色数据范围）

参考论文系统 `sys_organization` 表，用于保存角色可管理的学院、专业、班级、企业等数据范围。

```
sys_organization
  - organization_id（PK，自增）
  - account_id（关联 account.id）
  - user_id（关联 users.id，兼容论文系统字段）
  - role_id（关联 role.id）
  - dep_id（院系 ID，可为空）
  - profession_id（专业 ID，可为空）
  - class_id（班级 ID，可为空）
  - company_id（企业 ID，可为空）
  - cate_id（分类 ID，可为空，预留）
  - scope_key（生成列：dep/profession/class/company/cate 组合键）
  - enabled_flag（生成列：未禁用且未删除时为 1，否则为 NULL）
  - disabled: false / true（是否禁用）
  - created_at, updated_at, deleted_at

  **用途：** college_admin / profession_admin / enterprise 等角色的数据范围。一个账号可配置多行，用于管理多个学院、多个专业或多个企业。

  **唯一约束：** `(account_id, role_id, scope_key, enabled_flag)`，防止启用中的同一账号角色重复配置相同范围。`enabled_flag=NULL` 的禁用或删除记录不参与唯一限制。

  **查询索引：** `(role_id, disabled)`、`(dep_id, disabled)`、`(profession_id, disabled)`、`(class_id, disabled)`、`(company_id, disabled)`。
```

### students（学生档案）

```
students
  - student_id（PK，自增）
  - student_uuid（对外唯一标识）
  - user_id（关联 users）
  - name, student_num（学号）
  - grade_id（年级）, dep_id（院系）, profession_id（专业）
  - class_id（班级）, class_num（班号）
  - semester（学期/学年）
  - sex, birthday, mobile, email
  - avatar（头像）
  - education, school_type（学历/培养方式）
  - status: enabled / disabled
  - created_at, updated_at, deleted_at
```

### teacher_list（教师档案）

```
teacher_list
  - teacher_id（PK，自增）
  - teacher_uuid（对外唯一标识）
  - user_id（关联 users）
  - teacher_name, teacher_num（工号）
  - dep_id（所属学院）
  - teacher_class（职称）, education（学历）
  - sex, birthday, cellphone, email
  - avatar, signature（电子签名）
  - research_area（研究领域）, honor（荣誉）
  - is_visible_for_selection: false / true（学生选导时是否展示，默认 false）
  - selection_intro（选导展示介绍，可选）
  - status: enabled / disabled
  - created_at, updated_at, deleted_at
```

### grade_teacher_guide（教师指导容量）

```
grade_teacher_guide
  - id
  - teacher_id（关联 teacher_list）
  - grade_id（年级）, dep_id（院系）
  - max_choose_number（最大可选人数）
  - choose_number（已选人数）
  - remain_number（剩余可指导人数）
  - semester（学期）
  - created_at, updated_at, deleted_at

  **唯一约束：** `(teacher_id, grade_id, dep_id, semester)` 确保同一教师在同学期同年级同院系只有一条容量记录。
```

**用途：** 控制教师在不同年级/院系的可指导容量。跨学院指导时，同一教师在多个 dep_id 下各有容量记录。pair 表创建配对时需校验容量。

## 3. 角色切换

```
登录 → 查当前学校库 users → 查当前学校库 account → 选择当前账号
     → 查该账号所有角色 → 选择当前角色
     → 生成 JWT（含当前 user_id, account_id, role_id）
     → 进入对应页面

切换角色：
  - 前端触发切换 → 后端更新 JWT 中的 current_role
  - 无需重新登录，只需重新签发 token
  - 前端顶部常驻角色/账号切换入口
```

JWT Payload 结构（仅存储最小必要字段，附加信息由 CurrentContext 按需查询）：

```json
{
  "user_id": 1,
  "current_account_id": 10,
  "current_role_id": 3,
  "current_college_id": 5
}
```

`profession_id`、`class_id`、`company_id` 等角色上下文 ID 不存入 JWT，由 `CurrentContext::organizationScopes()`、`CurrentContext::professionId()` 等方法从 `sys_organization` 表或档案表（students/teacher_list）按需读取并缓存。

AuthMiddleware 验证 JWT 后将上述字段注入 Context，后续通过 `CurrentContext` 全局访问（见 `00-总体架构设计.md` 3.9 节）：

```php
$userId = CurrentContext::userId();
$accountId = CurrentContext::accountId();
$roleId = CurrentContext::roleId();
```

完整角色列表和账号列表通过 `GET /api/user/profile` 接口按需获取，不存入 JWT。

切换接口：
- `POST /api/user/switch-role` — 切换当前角色
- `POST /api/user/switch-account` — 切换当前学校库内账号

## 4. 用户服务边界

UserService（`app/server/user/`）职责：

- users 管理（自然人 CRUD）
- account 管理（账号绑定/解绑/自助管理）
- students 管理（学生档案 CRUD）
- teacher_list 管理（教师档案 CRUD）
- grade_teacher_guide 管理（指导容量配置）
- 企业微信绑定/解绑
- 当前学校库内账号自助绑定/解绑/切换
- 当前学校库内多账号管理（列表、设为主账号）
- 账号状态管理
- 角色分配
- 切换账号/角色

不负责：权限校验（权限中间件负责）、业务数据（各业务服务负责）。

## 5. 绑定校验流程

```
企业微信 OAuth 获取 userid
  → 查 users 表
     ├── 已绑定 → 查 students/teacher_list 确定身份 → 选身份 → 进主页
     └── 未绑定 → 跳转绑定页
           → 用户输入学号/工号 + 姓名
           → 后端调用外部校验接口核验
           → 校验通过 → 创建 users + account + students/teacher_list → 进主页
           → 校验不通过 → 提示"信息不匹配，请联系管理员"
```

外部校验预留为接口契约，后续实现具体适配器。

### 5.2 教务系统统一登录（预留）

PC 端支持通过学校教务系统 SSO 登录（CAS / OAuth / 统一身份认证）：

```
PC 端访问 → 选择"教务系统登录"
  → 跳转教务系统 SSO 页面
  → 用户在教务系统完成认证
  → 回调带 ticket/code
  → 后端调用 EduAdapter::authenticate(ticket, ...) 校验
     ├→ 校验通过 → 返回用户信息
     │    → 查 users 表
     │       ├→ 已存在 → 签发 JWT
     │       └→ 不存在 → 自动创建 users + account + students/teacher_list → 签发 JWT
     └→ 校验失败 → 提示"认证失败，请联系管理员"
```

配置项 `edu.auth_enabled` 控制是否启用教务系统登录入口。

### 5.3 自助绑定管理

用户登录后可在"个人中心 → 账号管理"查看、新增、删除当前学校库内的账号绑定。跨学校绑定需进入目标学校域名后完成，不通过当前学校库直接写入其他学校库。

**我的账号列表：**

```
GET /api/user/accounts

返回：
[
  {
    "account_uuid": "acc-a3f2...",
    "school_name": "A 大学",
    "roles": ["teacher"],
    "student_info": null,
    "teacher_info": {"teacher_name": "张三", "dep_name": "计算机学院"},
    "is_primary": true,
    "status": "enabled",
    "created_at": "2025-09-01"
  },
  {
    "account_uuid": "acc-b4e3...",
    "school_name": "B 学院",
    "roles": ["student"],
    "student_info": {"student_num": "2024001", "class_name": "软件工程2101"},
    "is_primary": false,
    "status": "enabled",
    "created_at": "2026-03-15"
  }
]
```

**新增绑定：**

```
POST /api/user/bind
{
  "identity_type": "student",        // student / teacher
  "identity_num": "2024001",         // 学号或工号
  "name": "李四"                     // 姓名（与档案匹配）
}

后端流程：
  1. 在当前学校库查 students/teacher_list 表
     → 匹配 identity_num + name
     → 不匹配 → 422 "信息不匹配，请核对"
  2. 匹配成功：
     → 查 users 表是否已有该档案关联的 user_id
       ├→ 已有 → 关联已有 users（极少情况）
       └→ 无 → 使用当前 users.id
     → 创建 account（关联当前学校库 users）
     → 创建 user_role（角色=student/teacher）
     → 返回新账号信息
  3. 记录操作日志
```

**限制规则：**

| 规则 | 说明 |
|---|---|
| 仅可绑定 student/teacher | 管理员角色不可自助绑定，需超级管理员分配 |
| 当前学校不可重复绑定 | 同一 users 在当前学校库已有 account 时拒绝 |
| 最多 5 个账号 | 防止滥用 |
| 需通过档案校验 | 学号/工号 + 姓名必须在目标学校档案中存在 |
| 企微用户优先 | 企微登录用户自动使用当前 wechat_userid 对应的 users |

**删除绑定：**

```
DELETE /api/user/accounts/{account_uuid}

限制：
  → 不可删除当前正在使用的账号（需先切换到其他账号）
  → 不可删除最后一个账号（至少保留一个）
  → 软删除 account（deleted_at），数据可恢复
  → 对应的 students/teacher_list 档案不删除（属于学校数据）
  → 记录操作日志
```

**切换主账号：**

```
POST /api/user/accounts/{account_uuid}/primary
  → 将指定账号设为 is_primary=true
  → 原 primary 账号自动取消
  → 主账号影响：默认登录后首选角色、消息通知优先发送
```

## 6. 双因子认证（2FA — PC 管理端）

仅管理员角色可用。默认关闭，管理后台手动开启。基于 TOTP（RFC 6238），兼容 Google Authenticator 等标准应用。

### 6.1 开启流程

```
管理员登录 PC 端
  → 进入"安全设置"页面
  → 点击"开启双因子认证"
  → 后端生成 TOTP 密钥 → 写入 account.two_factor_secret
  → 返回密钥 + QR Code URL（otpauth://totp/...）
  → 前端展示二维码
  → 管理员用 Authenticator 应用扫码
  → 输入应用显示的 6 位验证码
  → POST /api/user/verify-2fa { code }
  → 后端校验 TOTP → 通过 → account.two_factor_enabled = true
  → 后续登录必须输入 TOTP 验证码
```

### 6.2 登录流程

```
PC 端登录：
  1. 输入账号密码 → POST /api/auth/login
  2. 后端 `password_verify($input, $account->password)` 验证通过
     ├→ two_factor_enabled = false → 直接签发 JWT
     └→ two_factor_enabled = true → 返回 { require_2fa: true }
  3. 前端展示验证码输入框
  4. 输入 6 位 TOTP → POST /api/auth/verify-2fa { code }
  5. 后端校验通过 → 签发 JWT → 登录成功
  6. 连续 5 次错误锁定 2FA 30 分钟
```

### 6.3 关闭方式

**方式 A — 自行关闭：**

```
管理员登录后 → 安全设置 → 输入当前 TOTP 验证码确认
  → two_factor_enabled = false, two_factor_secret = null
```

**方式 B — 超级管理员强制关闭：**

```
超级管理员登录 → 用户管理 → 找到该管理员 → 关闭双因子认证
  → 无需验证码 → two_factor_enabled = false, two_factor_secret = null
  → 记录操作日志
```

管理员丢失 Authenticator 设备时，联系超级管理员执行方式 B。

## 7. 登录限流

基于 Redis 实现，防止暴力破解。

### 7.1 限流维度

| 维度 | Key | 规则 |
|---|---|---|
| IP + 账号 | `login_attempt:{ip}:{account}` | 同一 IP 对同一账号，5 分钟内最多 5 次 |
| IP 全局 | `login_attempt:{ip}:*` | 同一 IP 对所有账号，1 分钟内最多 20 次 |
| 账号全局 | `login_attempt:*:{account}` | 某账号被所有 IP 尝试，5 分钟内最多 10 次 |

### 7.2 触发策略

```
任意维度达到阈值：
  → 该维度锁定 5 分钟（Redis TTL）
  → 返回 HTTP 429 + "登录尝试过于频繁，请 5 分钟后重试"

单次登录过程：
  ├─ 密码错误 → 计数器 +1，返回"账号或密码错误"
  └─ 密码正确但 2FA 验证错误 → 2FA 计数器 +1（不触发登录限流，走 2FA 自身的 5 次锁定逻辑）
```

### 7.3 实现方式

全局中间件 `LoginThrottleMiddleware`，仅作用于 `/api/auth/login` 和 `/api/auth/verify-2fa` 路由。

**真实 IP 获取：**

```
获取顺序：
  1. X-Real-IP（nginx set_real_ip_from CDN 网段后设置，可信）
  2. X-Forwarded-For 第一个 IP（nginx 已剥离 CDN IP 时可信）
  3. REMOTE_ADDR（直接访问或 nginx 已处理后）
```

Nginx 配置（信任 CDN 回源 IP）：

```nginx
# 以阿里云 CDN 为例
set_real_ip_from 10.0.0.0/8;
set_real_ip_from 47.0.0.0/8;    # 实际按 CDN 厂商回源段配置
real_ip_header X-Forwarded-For;
real_ip_recursive on;
```

处理后 `REMOTE_ADDR` 即为真实客户端 IP，应用层直接读取即可。未经过 CDN 的请求，`X-Forwarded-For` 不可信，需确保 nginx 仅对 CDN 来源设置该头。

**计数器逻辑：**

```php
$ip = $request->getRealIp();
$key = "login_attempt:{$ip}:{$account}";

// Lua 脚本保证 INCR + EXPIRE 原子执行，避免进程崩溃导致 key 永不过期
$lua = <<<'LUA'
local count = redis.call('INCR', KEYS[1])
redis.call('EXPIRE', KEYS[1], ARGV[1])
return count
LUA;
$count = Redis::eval($lua, 1, $key, 300);

if ($count > 5) {
    throw new TooManyRequestsException('请 5 分钟后重试');
}
```

### 7.4 记录与告警

- 达到阈值时记录到 `operation_log`（module=system, action=login_blocked）
- 同一账号 1 小时内被锁定 3 次以上，可触发企微通知超级管理员

## 8. 教务系统对接服务

`app/server/edu/`，预留数据导入接口，用于从学校教务系统批量拉取学生、教师、班级、院系、专业等基础数据，替代手动录入。

### 8.1 驱动架构

```
app/server/edu/
```

### 8.2 适配器接口

```php
interface EduAdapter
{
    // === 基础数据拉取 ===
    public function fetchDepartments(): array;
    public function fetchProfessions(int $depId = null): array;
    public function fetchClasses(int $professionId = null, string $grade = null): array;
    public function fetchStudents(array $filters): array;
    public function fetchTeachers(int $depId = null): array;

    // === 业务数据同步 ===
    // 实习安排同步
    public function fetchArrangements(array $filters): array;
    // 师生配对同步
    public function fetchPairs(array $filters): array;

    // === 认证 ===
    public function authenticate(string $credential, string $password): ?array;

```

### 8.3 同步模式

预留两种模式，后续确定实际对接方式：

**模式 A — 定时拉取（pull）：**

```
系统定时任务（cron / webman scheduled task）
  → 按 sync_interval 间隔调用 EduAdapter::fetch*()
  → 增量 upsert 到本地表
  → 适合对方提供查询 API 的场景
```

**模式 B — 对方推送（push）：**

```
教务系统 → POST /api/edu/callback/{type}
  → 验证签名/密钥
  → 解析推送数据
  → upsert 到本地表
  → 返回 { status: 'ok' }
  → 适合对方有数据变更通知能力的场景
```

**配置项：**

```
edu:
  ├── sync_mode            同步模式（pull / push）
  ├── push_secret          推送验证密钥（push 模式用）
  └── sync_entities        同步实体范围（department,profession,class,students,teachers,arrangements,pairs）
```

### 8.4 同步流程

```
管理员操作（PC 端）：
  1. 选择教务系统类型 → 配置连接参数（API 地址/密钥等）
  2. 选择同步范围（全部 / 指定院系 / 指定年级）
  3. 点击"开始同步"
  4. 创建 export_task（type=edu_sync_*），Redis 队列异步执行
  5. 进度可追踪，完成后消息通知

同步逻辑：
  院系 → 专业 → 班级 → 教师 → 学生（按依赖顺序导入）
  每条记录按唯一标识（学号/工号）做 upsert
  不删除本地已有数据，仅新增或更新
```

## 9. 一键模拟登录（Impersonate）

高权限角色可生成一次性限时 URL，模拟低权限用户免密登录，用于管理员排查问题或辅助操作。

### 9.1 权限层级

```
super_admin   → 可模拟：school_admin, college_admin, profession_admin, teacher, student（当前学校库）
school_admin  → 可模拟：college_admin, teacher, student（仅本校）
college_admin → 可模拟：teacher, student（仅 sys_organization 覆盖范围）
teacher       → 可模拟：student（仅自己指导的学生）
student       → 不可模拟任何人
```

跨级限制：不可向上模拟（如 teacher 无法模拟 college_admin），不可平级模拟。

### 9.2 生成流程

```
管理员 PC 端操作：
  1. 进入用户列表 → 找到目标用户 → 点击"模拟登录"
  2. 前端 POST /api/admin/impersonate { target_account_uuid: "acc-a3f2..." }
  3. 后端校验：
     ├→ 操作者角色等级 > 目标角色等级 → 通过
     ├→ 操作者数据范围覆盖目标（同校/同院/同指导关系）→ 通过
     └→ 任一不满足 → 403
  4. 生成 32 位随机 token → Redis 写入：
     Key:   impersonate:{token}
     Value: {database_id, target_account_id, target_role_id, operator_user_id}
     TTL:   300（5 分钟）
     一次性：使用后立即 DEL
  5. 返回 URL：
     https://{domain}/api/auth/impersonate?token={token}
  6. 管理员复制 URL 发送给目标用户（企微/邮件/粘贴）
```

### 9.3 登录流程

```
用户点击链接（或粘贴到浏览器）：
  1. GET /api/auth/impersonate?token=xxx
  2. 后端查 Redis impersonate:{token}
     ├→ 不存在或过期 → "链接已失效，请重新获取"
     └→ 存在 → DEL 删除 key（一次性消费）
  3. 从 token 中获取 target_account_id, target_role_id, database_id
  4. 为该账号签发 JWT（含目标 user_id, account_id, role_id）
  5. 响应 Set-Cookie: jwt={new_token}（httpOnly）
  6. 302 重定向到 PC 端或 H5 端首页（根据 UA）
  7. 记录操作日志（module=system, action=impersonate, target=目标用户名）
```

### 9.4 安全约束

| 约束 | 说明 |
|---|---|
| 一次性 | token 使用后立即 DEL，不可重复使用 |
| 限时 | TTL 5 分钟，超时自动过期 |
| 不可猜测 | 32 位随机字符串（uuid v4） |
| 不可提权 | 只能模拟等级 <= 自己的角色 |
| 不可跨范围 | 学校管理员只能模拟本校用户 |
| 审计日志 | 每次模拟登录记录：操作者、目标用户、时间、IP |
| 操作者标记 | 操作日志中标记 `impersonated_by=operator_user_id`，可追溯 |

### 9.5 Redis 配置

```
Key:   impersonate:{token}
Value: JSON {database_id, account_id, role_id, operator_user_id, created_at}
TTL:   {impersonate_ttl} 秒（配置项 system.impersonate_ttl，默认 300）
```

### 9.6 管理界面（PC 端）

- 用户列表每行增加"模拟登录"按钮（仅当操作者有权模拟该用户时显示）
- 点击弹出确认框："您将以 {目标用户名} 身份登录，操作将被记录"
- 确认后生成链接，展示在弹窗中，提供"复制链接"按钮
- 操作日志中可筛选 `action=impersonate` 查看所有模拟登录记录

## 10. API Key 管理

用户可创建 API Key 供 Agent 或外部程序调用 API，替代 JWT 认证。管理员按用户开启此功能。

### 10.1 数据模型

```
api_key
  - id, uuid（对外标识）
  - account_id（关联 account）
  - name（用户命名的标识，如"Agent 调用"、"数据分析脚本"）
  - key_hash（SHA-256(actual_key)，不可逆）
  - key_prefix（前 8 位明文，如 "psk_a3f2b8c1"，列表识别用）
  - scopes（JSON 数组，如 ["read", "write"]，不能超出用户角色权限）
  - last_used_at（最后使用时间）
  - expires_at（过期时间，null=永久有效）
  - status: active / revoked
  - created_at, updated_at, deleted_at
```

### 10.2 开启条件

管理员在 PC 端"用户管理"中为用户开启 API Key 功能：

```
POST /api/admin/users/{account_uuid}/toggle-api-key  { enabled: true }
```

配置项 `user.api_key_enabled`（个人级，默认 false）。仅当该配置为 true 时，用户在"我的"页面才能看到 API Key 管理入口。

### 10.3 用户操作

**查看列表：**

```
GET /api/user/api-keys

返回：
[
  {
    "uuid": "a3f2...",
    "name": "Agent 调用",
    "key_prefix": "psk_a3f2b8c1",
    "scopes": ["read", "write"],
    "last_used_at": "2026-05-27 10:30:00",
    "expires_at": null,
    "status": "active",
    "created_at": "2026-05-01"
  }
]
```

**创建 Key：**

```
POST /api/user/api-keys
{
  "name": "Agent 调用",
  "scopes": ["read"],
  "expires_at": "2027-05-27"   // 可选，null=永久
}

后端：
  1. 校验 user.api_key_enabled = true
  2. 校验 scopes 不超出当前角色的权限范围
  3. 生成 40 位随机字符串：psk_{32位随机字符}
  4. 存储 SHA-256(key) 到 key_hash
  5. 存储前 8 位到 key_prefix
  6. 返回完整 key（仅此一次！）

响应：
{
  "uuid": "b4e3...",
  "name": "Agent 调用",
  "key": "psk_a3f2b8c1d4e5f6a7b8c9d0e1f2a3b4c5",  // 仅创建时返回
  "key_prefix": "psk_a3f2",
  "scopes": ["read"],
  "expires_at": "2027-05-27",
  "created_at": "2026-05-27"
}
```

前端展示 key 后弹出警告："请立即复制并安全保存此 Key，关闭后无法再次查看。"

**撤销 Key：**

```
DELETE /api/user/api-keys/{uuid}
  → status = revoked
  → 不可恢复
  → 立即生效（下次请求时 401）
```

### 10.4 认证流程

API Key 通过 `Authorization` 头传递：

```
GET /api/internship/students
Authorization: Bearer psk_a3f2b8c1d4e5f6a7b8c9d0e1f2a3b4c5
```

AuthMiddleware 认证流程：

```
1. 解析 Authorization 头
2. 判断前缀：
   ├→ "psk_" 开头 → API Key 认证
   │   → SHA-256(key) → 查 api_key 表 key_hash
   │   → 校验 status=active, expires_at 未过期
   │   → 从 api_key.account_id 加载用户信息 → 写入 Context
   └→ 无 API Key → 从 httpOnly Cookie 读取 JWT，走 JWT 认证流程
```

### 10.5 安全约束

| 约束 | 说明 |
|---|---|
| 不可查看 | Key 明文仅创建时返回一次，SHA-256 不可逆，丢失只能重新创建 |
| 权限不越级 | scopes 不能超过用户角色的接口权限 |
| 管理员控制 | 需管理员为每个用户单独开启 `user.api_key_enabled` |
| 操作日志 | 创建/撤销 key 均记录 operation_log（module=api_key） |
| 使用日志 | `last_used_at` 自动更新，可追踪 key 的最后活跃时间 |
| 每账号上限 | 最多 10 个 active key |
| 过期自动失效 | AuthMiddleware 校验 expires_at，过期返回 401 |

### 10.6 与 Agent 技能的对接

API Key 设计为后续 Agent 调用的凭证。Agent 使用 API Key 调用系统接口（如 `GET /api/stat/query`），AuthMiddleware 认证后获得对应用户的数据访问权限（受 DataScopeMiddleware 过滤），实现与用户同权限的数据查询。详见 `00-总体架构设计.md` 第 7 节。

## 11. 设备管理

用户可在"我的 → 设备管理"中查看所有已登录设备，并可远程下线非当前设备。

### 11.1 数据模型

```
user_device
  - id, uuid（对外标识）
  - account_id（关联 account）
  - jti（JWT ID，唯一标识该次登录）
  - device_name（设备名称，如 "Chrome on Windows"、"企业微信 on iPhone 15"）
  - ip（登录 IP）
  - user_agent（浏览器 UA 原文）
  - location（IP 归属地，如 "广东省广州市"）
  - last_active_at（最后活跃时间）
  - status: active / revoked
  - created_at（登录时间），updated_at, deleted_at
```

### 11.2 登录时记录设备

JWT Payload 增加 `jti`（JWT ID）：

```json
{
  "user_id": 1,
  "current_account_id": 10,
  "current_role_id": 3,
  "current_college_id": 5,
  "jti": "d4e5f6a7-b8c9-..."
}
```

登录成功后：

```
1. 生成 UUID 作为 jti → 写入 JWT
2. 前端生成 device_id（UUID，存入 localStorage，同设备跨会话不变）
3. 解析 UA → device_name（如 "Chrome 120 on Windows 10"、"WeChat 8.0 on iOS 17"）
4. IP 归属地查询（可选，通过 GeoIP 库或第三方 API）
5. INSERT user_device（account_id, jti, device_name, ip, user_agent, location）
6. 同 device_id 的旧记录自动标记 revoked（同一设备重复登录时清理旧会话）
```

```

返回：

    "uuid": "dev-a3f2...",
    "device_name": "Chrome on Windows",

    "location": "广东省广州市",
    "last_active_at": "2026-05-27 14:30:00",
    "is_current": true,           // 当前请求的设备
    "login_at": "2026-05-20 09:00:00"
  },
  {
    "uuid": "dev-b4e3...",
    "device_name": "企业微信 on iPhone 15",
    "ip": "119.xxx.xxx.xxx",
    "location": "北京市",
    "last_active_at": "2026-05-26 08:00:00",
    "is_current": false,
    "login_at": "2026-05-25 18:00:00"

]
```

### 11.4 删除设备（远程下线）

```
DELETE /api/user/devices/{device_uuid}

限制：
  → 不可删除当前设备（is_current=true 的记录不显示删除按钮）
  → 删除后：user_device.status = revoked
  → 对应 JWT 的 jti 加入 Redis 黑名单
      Key: jwt_blacklist:{jti}
      Value: 1
      TTL:  JWT 剩余有效时间（过期后自动清除，不占内存）
```

## 12. 消息通知偏好

用户可在"我的 → 消息通知"中配置接收消息的渠道和场景。

### 12.1 数据模型

```
user_notify_setting
  - id
  - account_id（关联 account）
  - msg_type（消息类型：system / alert / audit / todo / result）
  - channel（渠道：internal / wechat / sms / email）
  - enabled: true / false（默认 true）
  - created_at, updated_at
  - 唯一约束：(account_id, msg_type, channel)
```

### 12.2 默认值

新账号创建时自动插入全部类型×渠道组合，默认全部开启：

| msg_type | internal | wechat | sms | email |
|---|---|---|---|---|
| system（系统通知） | true | true | false | false |
| alert（异常告警） | true | true | true | false |
| audit（审核通知） | true | true | false | false |
| todo（待办提醒） | true | true | false | false |
| result（结果通知） | true | true | false | true |

### 12.3 用户接口

```
GET /api/user/notify-settings

返回：
{
  "system":  {"internal": true, "wechat": true, "sms": false, "email": false},
  "alert":   {"internal": true, "wechat": true, "sms": true,  "email": false},
  "audit":   {"internal": true, "wechat": true, "sms": false, "email": false},
  "todo":    {"internal": true, "wechat": true, "sms": false, "email": false},
  "result":  {"internal": true, "wechat": true, "sms": false, "email": true}
}

PATCH /api/user/notify-settings
{
  "system":  {"sms": true},
  "todo":    {"wechat": false}
}
// 仅传入需要变更的项，未传入的项保持不变
```

### 12.4 发送时生效

MessageService 发送消息时：

```
1. 查询消息模板 → 获取 channels 列表（模板定义的可用渠道）
2. 遍历 channels：
   ├→ 查 user_notify_setting
   │   ├→ enabled=true → 投递
   │   └→ enabled=false → 跳过该用户该渠道
   └→ 未配置 → 默认投递（向前兼容）
3. 至少一个渠道投递成功即为发送成功
```

```
  站内消息  [开关]    企微推送  [开关]
```
