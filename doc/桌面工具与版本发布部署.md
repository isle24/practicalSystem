# 桌面工具与版本发布部署

## 服务端升级

1. 更新完整仓库 `master`，其中包含编译后的 `server/public/pc` 和 `server/public/h5`。
2. 对已有学校库运行可重复执行的结构升级。编号为主库 `databases.database_id`，本地学校编号为 `1`：

```sh
cd server
php database/migrations/20260910_desktop_tools.php 1
php start.php restart -d
```

已有库不要运行 `database/init.php`；它用于初始化，不是本次增量升级入口。数据库工具手动执行的 SQL 位于 `server/database/updates/0.2.0-school-tools.sql`，其中 `ALTER TABLE` 只能执行一次。重复升级使用上述迁移命令。

新增 `user_note`、`system_release`、`system_release_sql`、`desktop_release_asset`，为 `favorite_link` 补充共享范围、打开方式、操作人及修订号。业务表均在学校库，主库无需变更。

本地学校库已经执行上述结构升级；学校后台仍需由管理员在“版本与更新 → 升级 SQL”登记实际执行情况。登记不会在线运行 SQL，也不意味着系统验证了人工执行的结果。

## 界面入口

- PC 启动台：收藏夹、记事本、更新说明。可以添加至个人桌面。
- 学校管理员新增或编辑收藏：打开“同步到全校”，确认后所有账号可见；用户自己选择是否添加到桌面。撤回共享后只对创建人可见。
- 个人记事本：新建多篇笔记，支持 Markdown 编辑、预览、搜索、回收站和恢复。保存修订号冲突时保留当前输入，不覆盖其他窗口的内容。
- H5：“我的 → 个人记事本 / 更新说明”。笔记和 PC 使用相同账号接口。
- PC：“系统配置 → 版本与更新”。超级管理员、学校管理员同时具备 `config:manage` 才可维护；其他角色无法请求后台详情或 SQL。

笔记正文、标题及搜索内容不进入请求参数审计，只保留接口用途、账号、笔记编号及结果。本机未提交草稿按学校和账号隔离；正式内容保存在学校数据库。

## GitHub 配置

GitHub 仓库 `isle24/practicalSystem` 只同步 `fontend/desktop`、`fontend/pc`、`fontend/shared`、构建工作流和客户端说明。不得同步 `server`、SQL、`.env` 或完整服务端提交历史。

在仓库 Actions Secrets 中配置：

| 名称 | 值 |
| --- | --- |
| `TAURI_SIGNING_PRIVATE_KEY` | 稳定的 Tauri 更新私钥文件内容 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 私钥密码 |

本机受限备份目录：`/Users/isle/.config/practical-system/signing/`。私钥文件为 `updater.key`，密码文件为 `updater-password`，公钥已编译进客户端。不要把私钥提交到 Git、填写到业务后台或发到聊天中。后续版本必须沿用本次公钥对应的私钥。

普通提交运行全平台构建。正式发布使用与客户端配置一致的标签 `v0.2.0`，或手动运行 `Desktop installers` 并开启 `publish`。三个平台都构建成功后才创建并公开 GitHub Release。Mac 通用包、Windows NSIS、Linux AppImage/deb 均由 Actions 生成。本机仅执行代码检查和前端编译。

2026-09-10 两项签名 Secrets 已配置，[三端构建及发布](https://github.com/isle24/practicalSystem/actions/runs/34456473667)全部通过，[v0.2.0 安装包](https://github.com/isle24/practicalSystem/releases/tag/v0.2.0)已发布。GitHub 收集产物时统一名称，发布前核对实际上传的名称、大小及 SHA256；服务端按清单中的同名资产导入。

每次升级同步修改 `fontend/desktop/package.json`、对应锁文件、`src-tauri/Cargo.toml`、`Cargo.lock` 和 `tauri.conf.json` 的版本；在 `fontend/desktop/releases/<版本>.md` 填写用户说明。构建生成 `desktop-release.json`、签名和 `SHA256SUMS.txt`。

## 学校发布流程

1. 为学校服务端创建只允许读取该 GitHub 仓库 Contents 的令牌，在 `server/.env` 配置 `DESKTOP_GITHUB_TOKEN`。不要使用开发者的高权限 Git 凭据。
2. 可选配置 `DESKTOP_GITHUB_REPOSITORY`，默认 `isle24/practicalSystem`。配置后重启 Webman HTTP 和 Redis 队列进程。
3. 管理员打开“版本与更新 → 客户端版本 → 从 GitHub 导入”，选定正式版本。
4. 下载任务通过 `desktop-release-download` Redis 队列执行，状态在安装包页签显示。下载后校验大小及 SHA256，并保存为正式文件引用。失败可以重试。
5. 管理员维护说明、核对必要 SQL 后点击“发布”，二次确认。导入和保存草稿都不会向用户发布。
6. 发布后 PC/H5 展示更新说明，客户端可提示升级。撤回版本会停止新升级并使已签发的该版本下载凭据失效。

随服务端部署的系统更新说明位于 `server/releases/*.json`，自动导入为草稿，不覆盖管理员修改。SQL 文件单独放 `server/database/updates/`，在版本清单中按顺序列出；不放进客户端资源。

## 客户端使用

收藏选择“客户端窗口”后，外部网页在独立原生窗口打开。“窗口”菜单支持后退、前进、刷新、复制当前网址和在浏览器打开。网页没有学校令牌或原生命令权限。学校设置、升级和学校附件预览仍由可信学校窗口处理。

客户端在登录后、回到前台和手动“检查更新”时检查当前学校已发布版本。用户确认后下载，校验通过后再次确认保存内容与退出，再覆盖安装。切换学校会取消旧会话的下载任务。正式在线安装仅支持 HTTPS。

| 平台 | 安装方式 |
| --- | --- |
| macOS Intel / Apple Silicon | 通用 DMG，拖入“应用程序”覆盖；后续使用签名 `.app.tar.gz` 更新 |
| Windows x64 | NSIS 安装器覆盖同一应用目录；在线升级显示安装进度 |
| Linux x64 AppImage | 使用签名 AppImage 更新，文件需要有写权限 |
| Linux x64 deb | 下载新版 deb 后使用系统软件安装器覆盖 |

旧版 `v0.1.0` 没有 updater，需要手动覆盖安装本次新版一次。应用标识和学校连接配置路径保持不变。Tauri 更新签名独立于 Apple 公证和 Windows Authenticode；未配置系统签名证书时仍可能出现操作系统来源提示。
