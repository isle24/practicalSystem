# 教务标准数据导入与企业微信配置检测设计

## 1. 建设边界

- 以“在校学生”“开课计划”“开课情况”三种 Excel 结构作为教务数据标准。
- 首次导入与后续教务系统对接共用同一套字段、来源键、校验、差异和发布规则。
- 教务源数据与实习、实验、实训、社会实践业务数据分层存储。
- 学生和教师导入只创建基础档案，不批量创建登录账号。
- 实习、实验、实训、社会实践候选数据经管理员确认后才生成业务草稿。
- 本次提供企业微信配置检测和默认菜单，不扩展完整 OAuth 首次绑定流程，不调用企业微信菜单发布接口。
- PC 端提供导入与确认界面，H5 不提供导入入口。

## 2. 源文件标准

### 2.1 在校学生

- 工作表名称固定为 `sheet1`。
- 保留原文件 44 个字段及顺序。
- 来源唯一键为学号。
- 学号、姓名、年级、学院、专业代码、专业名称、班号和班级为基础档案映射字段。
- 学籍状态、是否在校和有无学籍共同决定来源状态，不直接删除历史学生。

### 2.2 开课计划

- 工作表名称固定为 `sheet1`。
- 保留原文件 45 个字段及顺序。
- 来源键由学年、学期、年级、课程代码和专业代码生成。
- 开课部门代码和开课部门用于建立学院代码映射。
- 专业学院名称、专业代码和专业名称用于建立专业映射。

### 2.3 开课情况

- 工作表名称固定为 `sheet1`。
- 保留原文件 91 个字段及顺序。
- 来源唯一键为教学班 ID。
- 教工号、教师名称、教师部门、教师性别、出生日期、职称和人员类别用于教师档案同步。
- 多教师字段使用英文逗号分隔，各教师属性按相同下标对齐。
- 教学班组成使用英文分号分隔班级。

### 2.4 下载模板

- 提供“在校学生导入模板.xlsx”“开课计划导入模板.xlsx”“开课情况导入模板.xlsx”。
- 第一张工作表仅包含原始表头，不包含真实业务数据。
- 第二张工作表名称为“填写说明”，记录必填字段、主键、日期格式和多值分隔规则。
- 导入程序只解析 `sheet1`，忽略“填写说明”。

## 5. 导入与发布

### 5.1 两阶段处理

1. 文件上传后写入受保护文件分类并创建批次。
2. Consumer 按数据块读取 Excel，标准化后写入暂存表。
3. 完成表头、主键、重复行、字段格式和数据范围校验。
4. 与当前源数据比较并生成差异。
5. 管理员确认后，在事务中合并暂存数据并发布新快照。
6. 发布成功后同步基础档案并生成业务候选项。
7. 暂存、校验或发布失败不修改当前有效源数据。

`partial_failed` 只用于源数据已成功发布，但基础档案同步或业务候选生成未全部完成的情况。后续重试只补齐未完成步骤，不重复发布源数据。

### 5.2 快照规则

- 在校学生文件是学校级完整快照。
- 开课计划和开课情况文件是学年、学期范围内的完整快照。
- 新批次缺失的学生标记为待停用，经确认后停用，不删除档案和绑定账号。
- 新批次缺失的计划或教学班标记为来源已取消或失效。
- 已生成的业务数据只产生变更提示，不自动删除或覆盖。
- 后续教务接口按同一来源键执行增量更新，停开或删除必须显式传递状态。

### 5.3 基础档案

- 学院优先按开课部门代码匹配，名称用于校验和别名映射。
- 专业源标识为学院代码和专业代码。
- 现有业务按年级筛选专业，因此基础档案按“年级 + 学院 + 专业代码”建立年级专业记录。
- 班号唯一，班级继承年级、学院和专业映射。
- 可与教务数据匹配的演示档案更新为正式代码，无法匹配的演示档案停用。
- 现有演示业务记录保留。

### 5.4 教师档案

- 从开课情况按教工号拆分教师数据。
- 按教工号唯一更新 `teacher_list`。
- 教师部门按学院代码或名称映射。
- 主讲和辅讲保存在课程教师关系表，不写入教师档案固定属性。
- 不创建教师登录账号。

## 6. 业务分类

### 6.1 自动分类

按以下顺序判断：

1. 课程名称包含“社会实践”，分类为社会实践。
2. 课程名称包含“实习”，分类为实习。
3. 课程名称包含“实训”“实践”或“课程设计”，分类为实训。
4. 课程名称包含“实验”，分类为实验。
5. 无名称命中且实验总学时大于零、实践总学时为零，分类为实验。
6. 无名称命中且实践总学时大于零、实验总学时为零，分类为实训。
7. 只有“实践课”或“实践环节”标记的数据保持待分类。
8. 其余数据只保存在教务源数据层。

### 6.2 人工确认

- 明确分类的候选项可批量确认。
- 待分类项必须逐条选择实习、实验、实训、社会实践或忽略。
- 确认后只生成草稿，不直接进入审核、发布或执行状态。
- 相同来源和业务类型重复确认时执行幂等更新。

## 7. 敏感数据与身份校验

### 7.1 存储

- 身份证号、家庭地址、出生地和生源地等写入 AES-256-GCM 加密负载。
- 手机号生成 HMAC-SHA-256 校验值。
- 身份证后 6 位生成 HMAC-SHA-256 校验值，不保存可直接查询的后 6 位。
- 使用独立 `EDU_IDENTITY_ENCRYPTION_KEY`，不复用教师同步或其他业务密钥。
- 密钥缺失时批次失败，不允许降级为明文。
- 列表和预览只返回脱敏值。

### 7.2 学生校验

1. 按学校和学号定位当前学生源数据。
2. 比较标准化后的姓名。
3. 来源数据存在手机号时，比较企业微信手机号 HMAC。
4. 来源数据无手机号时，要求输入身份证后 6 位并比较 HMAC。
5. 成功后只返回学生档案 ID，不返回敏感字段。
6. 按学校、学号、企业微信 UserId 和 IP 限流，连续失败写入操作日志。

### 7.3 教师校验

- 当前使用教工号和姓名校验。
- 后续教务接口提供手机号后，增加手机号 HMAC 校验。
- 主讲和辅讲关系不参与教师身份校验。

## 8. 企业微信配置检测

### 8.1 检测流程

1. 校验 CorpId、AgentId、Secret 和代理地址。
2. 使用当前表单值调用企业微信 `gettoken`。
3. 获取访问凭证后调用 `agent/get`。
4. 校验返回应用的 AgentId。
5. 成功时返回应用名称、AgentId 和检测时间。
6. 失败时返回企业微信错误码和经过转换的错误信息。

检测不调用菜单创建、更新或删除接口，不修改已保存菜单。Secret 和访问凭证不写入操作日志。

### 8.2 密钥返回

- 已保存 Secret 只返回掩码和 `secret_configured` 状态。
- 保存时传入空值或掩码表示保持原密钥。
- 检测时输入新 Secret 则使用新值，否则使用已保存密钥。

### 8.3 默认菜单

- 菜单为空时生成一个名为“实践系统”的一级 `view` 菜单。
- 菜单地址是当前学校项目根地址的绝对 URL。
- 根入口继续由 `IndexController` 根据用户代理和屏幕宽度跳转 PC 或 H5。
- 已有菜单不自动覆盖。
- 地址为 localhost、127.0.0.1 或非 HTTPS 时显示部署警告。

## 11. 容量与异常处理

- Webman `max_package_size` 调整为 500MB。
- 部署配置同步要求 Nginx、PHP 和上游代理的请求限制不低于 500MB。
- 只允许 `xls` 和 `xlsx`。
- 校验 ZIP 解压体积和压缩比，拒绝疑似压缩炸弹的文件。
- 在校学生最多 500,000 行，开课计划和开课情况各最多 200,000 行。
- 同一学校、类型和学年学期只允许一个处理中批次。
- 相同 SHA-256 文件不重复执行。
- 队列任务最多自动重试 3 次，批次号和来源键保证幂等。
- 表头缺失、顺序错误、未知字段、主键缺失、主键冲突或必填字段格式错误会阻止发布。
- 由于文件是完整快照，存在未解决的主键或映射问题时，整个批次不能发布。
- 分类不明确不阻止源数据发布，但不允许直接生成业务草稿。

## 14. 实际导入记录

### 14.1 解析实现修正

原实现使用 PhpSpreadsheet `Xlsx` 读取器配合 `IReadFilter` 分块。实测该读取器在应用过滤器之前，会通过 `ZipArchive::getFromName()` 将整个工作表 XML 一次性读入字符串，内存占用由文件总大小决定，与 chunk size 无关，因此“分块”并不成立。

在校学生文件实测数据：`xl/worksheets/sheet1.xml` 压缩 8.6MB、解压 102,971,396 字节。在 `memory_limit=128M` 下消费者解析至 5% 时即触发内存溢出退出：

```text
Fatal error: Allowed memory size of 134217728 bytes exhausted
(tried to allocate 102971428 bytes) in .../Reader/Xlsx.php on line 415
```

同时 `EduImportService::parse()` 每 2000 行调用一次 `readChunk()`，而每次调用都会重新加载整个文件，33,418 行共触发 17 次全量加载。

修正方案：`EduSpreadsheetReader` 改为基于 `XMLReader` 的单次流式解析。

- 通过 `xl/workbook.xml` 与 `xl/_rels/workbook.xml.rels` 按工作表名 `sheet1` 定位目标表，不依赖固定文件名。
- 单元格值按 `t` 属性解析，支持 `inlineStr`、共享字符串 `s`、布尔 `b`、错误 `e` 与数值；共享字符串表同样流式读取。
- 压缩条目解压到临时文件，`XMLReader` 以文件方式打开，避免将 103MB XML 驻留内存。
- 读取游标由读取器持有，`readChunk()` 按行数推进，多次调用共享同一游标，整个过程只遍历工作表一次。
- `EduImportService::parse()` 在 `finally` 中释放读取器与临时文件。

PhpSpreadsheet 仅保留用于生成模板文件（有界的小文件写入），不再用于解析上传文件。

### 14.3 开课情况发布修正

开课情况路径在实测中暴露三个缺陷，均已修复。

其一，`diff()` 对数组值执行字符串转换。`mapAndSync()` 会把教师列表写入 `$data['teachers']`，随后 `diff($before, $data)` 遍历全部字段并逐个转换，遇到数组即触发 `Array to string conversion`，发布整体失败。修正为跳过数组与对象值，并在 `safeBefore()` 中排除 `teachers`，避免内部结构写入 `after_json`。

其二，`edu_course_offering_teacher` 写入不可达。`upsertSource()` 先执行 `unset($data['teachers'])`，之后才判断 `!empty($data['teachers'])`，条件恒为假，关系表始终为空。修正为在 `unset` 前保存教师列表。

其三，`edu_course_offering_class` 缺少写入实现。该表在设计与建表中存在，但没有任何代码向其写数据。已补 `syncOfferingClasses()`，按英文分号拆分教学班组成，逐班号写入并关联 `class_id`，同时把本次未出现的旧关系置为 `disabled`。

另修正一处流程缺陷：暂存数据缺失时 `publish()` 会以空循环“成功”结束并返回 completed。现增加显式校验，暂存为空时返回 409。同时 `publish()` 失败时回退到 `pending_confirm` 并记录 `error_message`，保留暂存数据以便重试。

以上修正通过合成样例验证（3 条教学班）：

| 关系表 | 结果 |
| --- | --- |
| `edu_course_offering_teacher` | 4 条，T001/T002 按教工号拆分并带 `sort`，`teacher_id` 正确关联 |
| `edu_course_offering_class` | 4 条，`计科2601班;计科2602班` 正确拆分为两条，`sort` 递增 |

合成样例的班号不存在于真实基础档案，`class_id` 为 NULL，`class_num` 正常记录。

### 14.4 主讲辅讲取值确认

真实文件已确认取值口径：`是否主讲` 按英文逗号与 `教工号` 一一对齐，取值为 `主讲` 或 `辅讲`（不是 `是`/`否`）。全表 5,088 行中 `主讲` 5,320 人次、`辅讲` 8 人次，`教工号` 与 `是否主讲` 数量不一致的行为 0。

`辅讲教师` 列仅在 8 行有值，与 `是否主讲` 中的 `辅讲` 重复，故不参与解析。

现有实现按逗号拆分并以 `$roles[$index]` 逐位取值，逻辑正确，无需修改。教师部门 `教师部门` 为单值列，多教师行重复同一值，实现以 `$departments[$index] ?? $departments[0]` 兼容，行为正确。

发布结果 `main` 5,320 条、`assistant` 8 条，与源文件完全一致。

### 14.5 验收不通过的根因与修正

首轮验收未通过，逐项核对发现实现层存在四类实质性错误，均不能仅凭行数判断。

#### 14.5.1 敏感字段明文残留

`raw_payload` 原仅剔除 6 个字段，`考生号` 33,418 行、`手机号码` 10,770 行以明文全量落库。原文档曾据此声称敏感字段已脱敏，该结论错误。

`EduImportNormalizer::SENSITIVE_STUDENT_FIELDS` 扩展为 10 项：`证件号`、`家庭地址`、`出生地`、`生源地`、`籍贯`、`政治面貌`、`手机号码`、`考生号`、`出生日期`、`电子邮箱`，并作为 `unset` 的白名单来源，两者共用同一常量，避免再次出现常量扩展而剥离逻辑未同步。

#### 14.5.2 专业与年级错配

`profession()` 以 `(dep_id, grade_id, name)` 为键，命中后回写 `grade_id`，导致同一专业在不同年级被反复改写归属。实测学生 `grade_id` 与所属专业 `grade_id` 不一致者 22,641 / 33,418。

改为以 `(dep_id, grade_id, profession_code)` 为键、代码缺失时回退名称，且不再回写 `grade_id`。同时 `department()`、`grade()`、`departmentId()` 由「代码与名称二选一」改为「名称或代码任一命中」，并在命中行缺少代码时回填。

#### 14.5.3 开课班级关联全空

`edu_course_offering_class.class_id` 全表 18,086 行为 0，原因是 `教学班组成` 存放的是班级名称，而查找仅比对 `class_num`。

新增 `EduStudentSyncService::resolveClassId()`，依次尝试 `class_num`、`class_name`、`class_short_name`。`class_id` 解析率由 0 提升至 17,628 / 18,086。

未解析的 458 行已逐条核实，均属合理缺口，非静默失败：

| 类别 | 数量 | 说明 |
| --- | --- | --- |
| 无效值 | 344 | `教学班组成` 取值为 `2025`、`2026`、`无`，非班级名称 |
| 档案无对应班级 | 114 | 该班级存在于开课计划但无学生，学生文件中不产生 `class` 行 |

对 114 条样本回查学生源数据，命中数均为 0，确认并非匹配逻辑遗漏。

#### 14.5.4 变更数与源行数不符

原发布逻辑逐行开启事务，且以 `edu_import_change` 回填计数，出现教学计划 3,590 / 3,591 的行数缺口。

改为解析阶段即在暂存行内预计算 `change_type`、`before_json`、`diff_json`、`classification_source`、`classification_reason`，发布阶段直接取用；最终计数以 `edu_import_change` 聚合为准。三类数据源行数与变更数现已逐一相等。

#### 14.5.5 暂存行丢失

`candidateStatus()` 仅依据 `business_type` 判断，`business_type` 为空但由标志列命中分类的行（教学计划 155 行、开课情况 144 行）不会进入候选项。修正后按 `business_type` 非空或 `classification_source='flag'` 判定，上述行已全部纳入。

### 14.6 发布事务与断点续传

整批发布改为分块事务：每 100 行一个事务，提交后立即删除对应暂存行并更新进度。

首版实现曾将整批纳入单个事务，实测 33,418 行学生导入在事务内累积 15,888 个行锁、41,235 行未提交修改，事务持续 265 秒且外部完全不可见，进程中断即全部回滚。该方案已废弃。

当前行为：进度按块可见，中断后重入同一接口即从剩余暂存行继续，已提交部分不受影响。发布锁 TTL 由 15 秒调整为 1,800 秒，避免长时发布期间锁提前过期导致并发重入。

### 14.8 候选项确认幂等

草稿写入与候选状态更新原不在同一事务内，且 `createPlan` 分支未被真正调用。

修正为：进入事务前先检查 `generated_business_id`，已生成直接跳过；事务内再次校验 `candidate_status='pending'`；草稿插入与状态更新同事务提交。

实测对同一候选连续确认两次：首次 `created=1`，第二次 `skipped=1`，`internship_plan` 仅新增 1 行。同时移除了仅允许 `teaching_plan` 来源的限制，使开课情况候选可正常生成草稿。
