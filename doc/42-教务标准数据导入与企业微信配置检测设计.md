# 教务标准数据导入与企业微信配置检测设计

## 1. 建设边界

- 以“在校学生”“开课计划”“开课情况”三种 Excel 结构作为教务数据标准。
- 首次导入与后续教务系统对接共用同一套字段、来源键、校验、差异和发布规则。
- 教务源数据与实习、实验、实训、社会实践业务数据分层存储。
- 学生和教师导入只创建基础档案，不批量创建登录账号。
- 实习、实验、实训、社会实践候选数据经管理员确认后才生成业务草稿。
- 本次提供企业微信配置检测和默认菜单，不扩展完整 OAuth 首次绑定流程，不调用企业微信菜单发布接口。
- PC 端提供导入与确认界面，H5 不提供导入入口。

## 2. 源文件标准

### 2.1 在校学生

- 工作表名称固定为 `sheet1`。
- 保留原文件 44 个字段及顺序。
- 来源唯一键为学号。
- 学号、姓名、年级、学院、专业代码、专业名称、班号和班级为基础档案映射字段。
- 学籍状态、是否在校和有无学籍共同决定来源状态，不直接删除历史学生。

### 2.2 开课计划

- 工作表名称固定为 `sheet1`。
- 保留原文件 45 个字段及顺序。
- 来源键由学年、学期、年级、课程代码和专业代码生成。
- 开课部门代码和开课部门用于建立学院代码映射。
- 专业学院名称、专业代码和专业名称用于建立专业映射。

### 2.3 开课情况

- 工作表名称固定为 `sheet1`。
- 保留原文件 91 个字段及顺序。
- 来源唯一键为教学班 ID。
- 教工号、教师名称、教师部门、教师性别、出生日期、职称和人员类别用于教师档案同步。
- 多教师字段使用英文逗号分隔，各教师属性按相同下标对齐。
- 教学班组成使用英文分号分隔班级。

### 2.4 下载模板

- 提供“在校学生导入模板.xlsx”“开课计划导入模板.xlsx”“开课情况导入模板.xlsx”。
- 第一张工作表仅包含原始表头，不包含真实业务数据。
- 第二张工作表名称为“填写说明”，记录必填字段、主键、日期格式和多值分隔规则。
- 导入程序只解析 `sheet1`，忽略“填写说明”。

## 4. 数据表

### 4.1 `edu_import_batch`

| 字段 | 用途 |
| --- | --- |
| id, uuid | 批次标识 |
| import_type | student / teaching_plan / course_offering |
| file_id | 原始文件 |
| file_sha256 | 文件去重 |
| academic_year, semester | 开课数据快照范围 |
| status | queued / parsing / validating / pending_confirm / publishing / completed / partial_failed / failed / cancelled |
| total_rows, valid_rows, invalid_rows | 解析统计 |
| created_count, updated_count, missing_count, disabled_count | 差异统计 |
| progress | 处理进度 |
| error_message | 批次失败原因 |
| created_by, confirmed_by | 操作人 |
| confirmed_at, completed_at | 处理时间 |
| created_at, updated_at | 审计时间 |

索引：

- `(import_type, status, created_at)`
- `(academic_year, semester, import_type)`
- `file_sha256`

### 4.2 `edu_student_source`

- 学号唯一。
- 保存基础档案字段、来源状态、行摘要、当前批次和原始非敏感 JSON。
- 保存加密敏感负载、手机号 HMAC 和身份证后 6 位 HMAC。
- 保存已映射的 grade_id、dep_id、profession_id、class_id 和 student_id。

索引：

- 唯一索引 `student_num`
- `(grade_code, dep_code, profession_code, class_num)`
- `(status, last_seen_batch_id)`
- `mobile_hmac`

### 4.3 `edu_teaching_plan_source`

- `source_key` 为学年、学期、年级、课程代码和专业代码的标准化 SHA-256。
- 保存原始字段、行摘要、映射 ID、业务分类和候选状态。

索引：

- 唯一索引 `source_key`
- `(academic_year, semester, status)`
- `(grade_code, dep_code, profession_code)`
- `(business_type, candidate_status)`
- `(course_code, academic_year, semester)`

### 4.4 `edu_course_offering_source`

- 教学班 ID 唯一。
- 保存课程、教学班、学时、周次、地点、教师、班级、开课状态和原始 JSON。
- 保存映射 ID、业务分类和候选状态。

索引：

- 唯一索引 `teaching_class_id`
- `(academic_year, semester, status)`
- `(course_code, academic_year, semester)`
- `(business_type, candidate_status)`
- `(last_seen_batch_id, source_status)`

### 4.5 关系表

`edu_course_offering_teacher`：

- 保存教学班、教工号、教师 ID和主讲/辅讲关系。
- 唯一索引 `(offering_id, teacher_num)`。
- 查询索引 `(teacher_num, offering_id)`。

`edu_course_offering_class`：

- 保存教学班、班号和班级 ID。
- 唯一索引 `(offering_id, class_num)`。
- 查询索引 `(class_num, offering_id)`。

### 4.6 批次处理表

`edu_student_stage`、`edu_teaching_plan_stage`、`edu_course_offering_stage`：

- 只保留正在处理的标准化数据。
- 唯一索引 `(batch_id, source_key)`。
- 查询索引 `(batch_id, row_number)`。
- 发布或取消后清理。

`edu_import_change`：

- 记录新增、更新、缺失、停用及具体字段差异。
- 唯一索引 `(batch_id, entity_type, source_key)`。
- 查询索引 `(batch_id, change_type, confirm_status)`。

`edu_import_issue`：

- 记录行号、字段、问题类型、提示和处理状态。
- 查询索引 `(batch_id, resolved, row_number)` 和 `(issue_type, resolved, created_at)`。

`edu_business_candidate`：

- 记录来源类型、来源 ID、业务类型、映射范围、分类依据、确认人和已生成业务 ID。
- 唯一索引 `(source_type, source_id, business_type)`。
- 查询索引 `(candidate_status, business_type, created_at)` 和 `(grade_id, dep_id, profession_id, candidate_status)`。

## 5. 导入与发布

### 5.1 两阶段处理

1. 文件上传后写入受保护文件分类并创建批次。
2. Consumer 按数据块读取 Excel，标准化后写入暂存表。
3. 完成表头、主键、重复行、字段格式和数据范围校验。
4. 与当前源数据比较并生成差异。
5. 管理员确认后，在事务中合并暂存数据并发布新快照。
6. 发布成功后同步基础档案并生成业务候选项。
7. 暂存、校验或发布失败不修改当前有效源数据。

`partial_failed` 只用于源数据已成功发布，但基础档案同步或业务候选生成未全部完成的情况。后续重试只补齐未完成步骤，不重复发布源数据。

### 5.2 快照规则

- 在校学生文件是学校级完整快照。
- 开课计划和开课情况文件是学年、学期范围内的完整快照。
- 新批次缺失的学生标记为待停用，经确认后停用，不删除档案和绑定账号。
- 新批次缺失的计划或教学班标记为来源已取消或失效。
- 已生成的业务数据只产生变更提示，不自动删除或覆盖。
- 后续教务接口按同一来源键执行增量更新，停开或删除必须显式传递状态。

### 5.3 基础档案

- 学院优先按开课部门代码匹配，名称用于校验和别名映射。
- 专业源标识为学院代码和专业代码。
- 现有业务按年级筛选专业，因此基础档案按“年级 + 学院 + 专业代码”建立年级专业记录。
- 班号唯一，班级继承年级、学院和专业映射。
- 可与教务数据匹配的演示档案更新为正式代码，无法匹配的演示档案停用。
- 现有演示业务记录保留。

### 5.4 教师档案

- 从开课情况按教工号拆分教师数据。
- 按教工号唯一更新 `teacher_list`。
- 教师部门按学院代码或名称映射。
- 主讲和辅讲保存在课程教师关系表，不写入教师档案固定属性。
- 不创建教师登录账号。

## 6. 业务分类

### 6.1 自动分类

按以下顺序判断：

1. 课程名称包含“社会实践”，分类为社会实践。
2. 课程名称包含“实习”，分类为实习。
3. 课程名称包含“实训”“实践”或“课程设计”，分类为实训。
4. 课程名称包含“实验”，分类为实验。
5. 无名称命中且实验总学时大于零、实践总学时为零，分类为实验。
6. 无名称命中且实践总学时大于零、实验总学时为零，分类为实训。
7. 只有“实践课”或“实践环节”标记的数据保持待分类。
8. 其余数据只保存在教务源数据层。

### 6.2 人工确认

- 明确分类的候选项可批量确认。
- 待分类项必须逐条选择实习、实验、实训、社会实践或忽略。
- 确认后只生成草稿，不直接进入审核、发布或执行状态。
- 相同来源和业务类型重复确认时执行幂等更新。

## 7. 敏感数据与身份校验

### 7.1 存储

- 身份证号、家庭地址、出生地和生源地等写入 AES-256-GCM 加密负载。
- 手机号生成 HMAC-SHA-256 校验值。
- 身份证后 6 位生成 HMAC-SHA-256 校验值，不保存可直接查询的后 6 位。
- 使用独立 `EDU_IDENTITY_ENCRYPTION_KEY`，不复用教师同步或其他业务密钥。
- 密钥缺失时批次失败，不允许降级为明文。
- 列表和预览只返回脱敏值。

### 7.2 学生校验

1. 按学校和学号定位当前学生源数据。
2. 比较标准化后的姓名。
3. 来源数据存在手机号时，比较企业微信手机号 HMAC。
4. 来源数据无手机号时，要求输入身份证后 6 位并比较 HMAC。
5. 成功后只返回学生档案 ID，不返回敏感字段。
6. 按学校、学号、企业微信 UserId 和 IP 限流，连续失败写入操作日志。

### 7.3 教师校验

- 当前使用教工号和姓名校验。
- 后续教务接口提供手机号后，增加手机号 HMAC 校验。
- 主讲和辅讲关系不参与教师身份校验。

## 8. 企业微信配置检测

### 8.1 检测流程

1. 校验 CorpId、AgentId、Secret 和代理地址。
2. 使用当前表单值调用企业微信 `gettoken`。
3. 获取访问凭证后调用 `agent/get`。
4. 校验返回应用的 AgentId。
5. 成功时返回应用名称、AgentId 和检测时间。
6. 失败时返回企业微信错误码和经过转换的错误信息。

检测不调用菜单创建、更新或删除接口，不修改已保存菜单。Secret 和访问凭证不写入操作日志。

### 8.2 密钥返回

- 已保存 Secret 只返回掩码和 `secret_configured` 状态。
- 保存时传入空值或掩码表示保持原密钥。
- 检测时输入新 Secret 则使用新值，否则使用已保存密钥。

### 8.3 默认菜单

- 菜单为空时生成一个名为“实践系统”的一级 `view` 菜单。
- 菜单地址是当前学校项目根地址的绝对 URL。
- 根入口继续由 `IndexController` 根据用户代理和屏幕宽度跳转 PC 或 H5。
- 已有菜单不自动覆盖。
- 地址为 localhost、127.0.0.1 或非 HTTPS 时显示部署警告。

## 11. 容量与异常处理

- Webman `max_package_size` 调整为 500MB。
- 部署配置同步要求 Nginx、PHP 和上游代理的请求限制不低于 500MB。
- 只允许 `xls` 和 `xlsx`。
- 校验 ZIP 解压体积和压缩比，拒绝疑似压缩炸弹的文件。
- 在校学生最多 500,000 行，开课计划和开课情况各最多 200,000 行。
- 同一学校、类型和学年学期只允许一个处理中批次。
- 相同 SHA-256 文件不重复执行。
- 队列任务最多自动重试 3 次，批次号和来源键保证幂等。
- 表头缺失、顺序错误、未知字段、主键缺失、主键冲突或必填字段格式错误会阻止发布。
- 由于文件是完整快照，存在未解决的主键或映射问题时，整个批次不能发布。
- 分类不明确不阻止源数据发布，但不允许直接生成业务草稿。

## 12. 首次导入

目标数据库为当前默认学校库 `practical_default`。

源文件核对基线：

- 在校学生 33,418 条，学号无重复。
- 开课计划 3,591 条，复合来源键无重复。
- 开课情况 5,088 条，教学班 ID 无重复。
- 开课情况可拆分出 1,429 个教工号。

执行顺序：

1. 导入“开课计划.xlsx”并发布源数据。
2. 导入“在校学生.xlsx”并发布学生及基础档案。
3. 导入“开课情况.xlsx”并发布教学班及教师档案。
4. 核对学生、教师、学院、年级、专业、班级、计划和教学班数量。
5. 核对新增、更新、缺失、停用、问题和业务候选数量。
6. 保留现有演示业务记录，停用无法匹配的演示基础档案。
7. 不自动确认业务候选项。

## 13. 交付验证

- 执行变更文件的 PHP 语法检查。
- 执行数据库初始化，核对表、字段、唯一索引和查询索引。
- 执行 PC 生产构建并同步静态产物。
- 通过实际三个文件完成上传、解析、差异、发布和数量核对。
- 检查重复文件、重复来源键、缺失记录、分类不明确数据和批次互斥。
- 检查学生手机号和身份证后 6 位校验不返回原始敏感值。
- 检查企业微信配置检测不发布菜单，Secret 和访问凭证不出现在响应明文和操作日志中。
- 不创建任何测试文件。
